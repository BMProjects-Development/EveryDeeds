# _tasks.md

Список конкретных задач для ИИ-агента. Перед началом работы — обязательно прочитать `AGENTS.md` целиком (там весь архитектурный контекст проекта). Задачи выполняются по порядку сверху вниз, если не указано иное. Не начинать следующую задачу, пока текущая не отмечена выполненной и не подтверждена автором.

## Задача 1: Экран прогресса (`TabloScreen`) — UI-каркас без реальных данных

**Цель**: собрать рабочий, кликабельный клиентский экран по описанию из раздела «Клиентская часть (UI)» в `AGENTS.md`, на **тестовых/заглушечных данных**. Реальная интеграция с серверным прогрессом (`PlayerAchievementData`, пакеты sync) — это отдельная задача, сюда не входит.

### Что должно быть готово по итогу

1. **Сайдбар категорий** слева:
   - Пункты: `Blocks`, `Items`, `Entities`.
   - Клик по пункту переключает активную категорию.
   - Активный пункт визуально явно отличается от неактивных (не только акцентной полоской — нужен отдельный стиль: фон/цвет текста и т.п., см. замечание в `AGENTS.md`).

2. **Панель контента справа** — вертикальный скролл (колесо мыши + желательно скроллбар), БЕЗ zoom и БЕЗ drag-pan.
   - Контент разбит на группы по источнику предметов (на тестовых данных достаточно 2-3 группы, например `Minecraft`, `TestModA`, `TestModB`, с разным количеством элементов в каждой — чтобы сразу проверить и мало, и много элементов в группе).
   - У каждой группы — заголовок-разделитель. Заголовок должен быть sticky (прилипает к верху видимой области при скролле содержимого своей группы).
   - Внутри группы — сетка ячеек фиксированного размера, которые заполняют доступную ширину панели (пересчёт числа столбцов при изменении ширины окна).

3. **Ячейка**:
   - Слот нейтрального/серого цвета (не красный — это был только плейсхолдер в мокапе).
   - Внутри — превью объекта. Для первого прохода допустима заглушка (см. `AGENTS.md`, пункт про live-превью), но:
     - структура ячейки должна принимать компонент рендера без переделки;
     - оставить явный `// TODO:` с описанием, что здесь должен быть живой рендер блока/выпавшего предмета/головы сущности, а не финальная реализация.
   - Hover-состояние: подсветка/рамка при наведении, реализованная через внешнее поле состояния (не через мутацию переменной в замыкании — см. «Известный баг» в `AGENTS.md`, не повторять его).
   - Тултип при наведении: имя объекта, id, тестовая строка прогресса (например «Добыто: 3/∞» — сами данные заглушечные, но формат должен соответствовать будущему реальному тултипу: категория действия + количество).

4. **Попап по клику (ЛКМ по ячейке)**:
   - Открывается поверх текущего экрана (не заменяет его).
   - Показывает: имя/id объекта, список требований (тестовые — по одному на каждое действие категории: для Blocks — Увидено/Добыто/Поставлено, для Items — Подобрано/Выброшено/Получено, для Entities — Увидено/Убито/Получено урона), для каждого требования — статус (выполнено / не выполнено, невыполненное — как «не изучено» либо «больше N не изучено»).
   - Закрывается по клику вне попапа или по отдельной кнопке закрытия.

5. **Виртуализация рендера**: рендерятся и хит-тестятся только видимые ячейки (см. алгоритм с префиксными суммами высот групп в `AGENTS.md`). Это требование — не «сделай, если успеешь», а часть задачи: экран должен нормально держать хотя бы несколько тысяч тестовых элементов без просадки фреймрейта, иначе задача не считается выполненной.

6. **Источник тестовых данных** — вынести за отдельный интерфейс/провайдер (например `TestAchievementDataSource` или аналог), а не хардкодить прямо внутри `Screen`/виджетов. Цель — чтобы в следующей задаче реальный снапшот прогресса подключался заменой одной реализации интерфейса, без переписывания рендера/виртуализации/хит-теста.

### Явно НЕ входит в эту задачу

- Реальная серверная логика (`AchievementTracker`, событийный слой, миксины, пакеты).
- Реальный `AchievementDefinition`/JSON/codec/датаген.
- Полноценный 3D live-рендер блока/выпавшего предмета/головы сущности внутри ячейки (заглушка допустима, см. выше).
- Фильтрация/поиск по сетке (если не попросит автор отдельно).

### Критерий готовности

- Экран открывается, категории переключаются.
- Скролл плавный, работает на нескольких тысячах тестовых элементов без явных просадок.
- Заголовки групп sticky.
- Сетка адаптируется по ширине при ресайзе окна.
- Наведение показывает тултип с корректными (тестовыми) данными по конкретной наведённой ячейке.
- Клик открывает попап с тестовым списком требований и их статусами.
- Код структурно разделяет «источник данных» и «рендер/виртуализацию» — переход на реальные данные в будущем не должен требовать переписывания виджета.

## Задача 3: доработки после первой версии — выполнено (ждёт проверки автором)

### Главное
0. Отфильтровать ачивки, которые физически нельзя выполнить: головка поршня, барьер, блок пустоты и т.п. Пройтись по всем категориям и действиям, дополнить теги `everydeeds:technical` / `everydeeds:unobtainable` (и, где нужно, трейты), проверить, что такие объекты не попадают в индекс.

### Косяки
1. Вода и лава не рендерятся как блоки (у жидкостей нет обычной модели). Нужен хотя бы вид по дефолтному стейту.
2. В сетке иконки должны быть 2D, как в инвентаре (блоки под углом). 3D-модель только в фокусе при наведении и в попапе.
3. У кроватей рендерится только половина (ноги).
4. Плоские блоки (стёкла, решётки) показывать со стейтом `west=true, east=true`, чтобы было видно.
5. У стола зачарований книжка лежит боком, а должна парить, как обычно.
6. Вращающимся предметам убрать покачивание вверх-вниз: только вращение.
7. Некоторые сущности рендерятся своим яйцом призыва (фолбэк), а не моделью.

### Пожелания
1. Фокус при наведении показывать с задержкой, а на ячейке визуально показывать заполнение (например, белым).
2. Показывать только начатые или законченные ячейки. Сортировка: сначала законченные, потом в процессе (выделять цветом).
3. Кнопка «Отобразить оставшиеся»: в самый конец списка добавляет ещё не полученные, красным.
4. Конфиг: размер ячеек и степень зума фокуса.
5. Конфиг: цвета.
6. Полосу заголовка группы («Minecraft … 89 entries») растянуть на всю ширину.
7. Кастомный тост в стиле основного меню, с краткой информацией.
8. Переключатель сложности (набора) в UI: в низу сайдбара, под категориями, слайдер с делениями short / extended / insane / maniac (+ кастомные наборы, если есть). Набор — настройка мира на сервере, поэтому переключение идёт через C2S-пакет -> сервер проверяет права (оператор, как у `/everydeeds set`) -> пересборка индекса и полный sync. Без прав — слайдер только показывает текущий набор.
