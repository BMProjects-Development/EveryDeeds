# AGENTS.md — EveryDeeds (mod id: `eds`)

Контекст для агента (Codex), работающего над этим репозиторием. Читай целиком перед тем, как что-либо менять или генерировать.

## Что это за мод

**EveryDeeds** — Minecraft-мод (Fabric + NeoForge, multi-loader), реализующий расширенную систему достижений поверх (и сверх) ванильной статистики. Смысл не в «списке предметов для сбора», а в учёте **действий** игрока с каждым блоком/предметом/сущностью в игре, с настраиваемой глубиной детализации (см. «Уровни сложности» ниже).

Мод делается автором в первую очередь для себя (мотивационный челлендж), но архитектурно должен быть чистым, расширяемым и без костылей — не «на отвяжись».

Разговорное прежнее название — `LedgerAll`; финальное — **EveryDeeds**, `modid = eds`, maven group `ru.benos`.

## Стек и окружение

- **Языки**: Kotlin — основной язык логики; Java используется точечно для Mixins (миксины пишутся на Java, если это удобнее/стандартнее для конкретного инжекта — уточнять по месту, не насаждать Java там, где Kotlin справится не хуже).
- **Лоадеры**: Fabric и NeoForge, через связку **Stonecutter + Architectury Loom** (уже отработанный у автора multi-version/multi-loader сетап на других его модах).
- **Версия Minecraft**: 26.3 (актуальная на момент старта проекта; сборка должна быть готова к последующим апдейтам через Stonecutter).
- **Fabric Loader**: 0.19.5 (пример из gradle.properties; сверяться с актуальной на момент работы).
- **Fabric Language Kotlin**: обязателен как зависимость (мод на Kotlin).
- **Java toolchain**: таргет 25.
- **Gradle**: Kotlin DSL (`build.gradle.kts`), не Groovy.
- **Split source sets**: используется `loom.splitEnvironmentSourceSets()` — чёткое разделение `main` (общая логика, работает и на сервере) и `client` (рендер/GUI/тосты). Серверная логика **не должна** ссылаться на клиентские классы ни при каких обстоятельствах — это должно быть невозможно на уровне компиляции, а не «на словах».
- **Datagen**: `fabricApi.configureDataGeneration`, используется активно (см. ниже).

### Известная gradle-ловушка (уже словили один раз, не наступать снова)

В `build.gradle.kts` НЕ объявлять свою функцию верхнего уровня с именем `property(key: String)` — она конфликтует с методом `Task.property(String): Any`, унаследованным `ProcessResources` и другими тасками. Внутри task-блоков (`tasks.processResources { ... }`) неявный receiver — сама таска, и member-функция всегда приоритетнее top-level при разрешении имён в Kotlin, поэтому вызов резолвится не туда. Либо использовать `project.property(...)` явно, либо назвать свою хелпер-функцию иначе (например `prop(...)`), не пересекаясь с методом `Task`.

## Архитектурная модель

### Server-authoritative, тонкий клиент

Вся логика трекинга прогресса, хранение данных и принятие решений «выполнено/не выполнено» — **только на сервере**. Клиент:
- получает пакеты о своём прогрессе (инкременты, разблокировки, полный снапшот при входе в мир);
- умеет запросить синхронизацию (`C2S RequestAchievementSyncPacket` → `S2C AchievementSyncPacket`);
- рендерит UI на основе локально закэшированного снапшота (без постоянных сетевых запросов на каждый чих UI, например на каждый ховер тултипа).

Мод обязателен к установке на сервере (не работает как чисто клиентский аддон) — это не «фича», а прямое следствие server-authoritative модели.

### Категории и действия

Три базовые категории, каждая — со своим набором действий:

- **Блоки**: Увидено, Добыто, Поставлено (+ возможные доп. действия по мере проработки).
- **Предметы**: Подобрано, Выброшено, Получено (крафт/переплавка и т.п.) (+ доп.).
- **Сущности**: Увидено, Убито, Получено (урон от этой сущности) (+ доп.).

Одно и то же смысловое действие («увидено») должно переиспользовать один и тот же базовый визуальный/понятийный символ между категориями, а не изобретаться заново под каждую — это касается и UI-иконок, и, по возможности, внутреннего именования типов действий.

### Источники событий (важно: не всё покрывается одинаково)

**Fabric API** покрывает лишь часть нужных действий нативно:
- `PlayerBlockBreakEvents.AFTER` — добыча блока. Есть.
- `AttackEntityCallback`, `UseBlockCallback`, `UseItemCallback` — есть, но это «попытка», не всегда факт завершения действия.
- Постановка блока, подбор предмета, выброс предмета, крафт, убийство/смерть сущности — **нативных событий в Fabric API нет** (подтверждено открытым issue в репозитории fabric-api на добавление события постановки блока).

Из-за этого пробела — рекомендованный подход: **единая точка перехвата через Mixin на `StatHandler#setStat`** (или его актуальный на 26.3 аналог), а не набор мелких миксинов на каждое действие по отдельности. Ванильная статистика уже инкрементируется при добыче, крафте, подборе, выбросе — так что один миксин в этой точке закрывает разом всё, что уже трекается `Stats`. То, чего в ванильной статистике нет вообще (постановка блока, «увидено» для блоков/сущностей, урон от конкретной сущности) — требует точечных миксинов в соответствующих местах (`Level#setBlock`, `LivingEntity#hurt` и т.п.).

**NeoForge**, в отличие от Fabric API, имеет заметно более богатый нативный event bus (`BlockEvent.EntityPlaceEvent`, `PlayerEvent.ItemPickupEvent`, `PlayerEvent.ItemCraftedEvent`, `LivingDeathEvent` и т.д.) — на NeoForge большую часть логики можно и нужно реализовывать через штатные события без миксинов, common-код должен уметь работать в обоих режимах без дублирования бизнес-логики (события/миксины — просто разные «источники сигналов», ведущие к одному и тому же общему `AchievementTracker.recordAction(...)`).

### Определения ачивок (definitions) — не хардкод, а данные

`AchievementDefinition` — JSON-модель (через kotlinx-serialization или vanilla `Codec`, определиться по месту, но не изобретать свой формат/язык парсинга — обычный JSON+codec полностью закрывает потребности). Загружается как datapack-ресурс через `ResourceReloadListener`, а не компилируется в код — это даёт возможность серверам/паку кастомизировать список без пересборки мода, и это прямая основа для `custom`-режима.

**Условия выполнения (predicates)** — рекурсивное дерево на sealed interface:

```kotlin
sealed interface Predicate {
    data class And(val predicates: List<Predicate>) : Predicate
    data class Or(val predicates: List<Predicate>) : Predicate
    data class Not(val predicate: Predicate) : Predicate
    data class HasEnchantment(val id: ResourceLocation, val minLevel: Int = 1) : Predicate
    // HasItem, HasBlockState, DurabilityAtLeast, и т.д. — листовые узлы
}
```

Сериализация — через `Codec.recursive` (или аналог в выбранном serialization-стеке). **Никакого собственного DSL/языка с ручным парсером — сознательно отвергнутая идея**, цена входа (lexer/parser/AST) не оправдана на фоне готового JSON-дерева.

### Уровни сложности (density) и датаген

Датаген генерирует `AchievementDefinition` JSON-ы для встроенных (не custom) уровней. Четыре уровня:

1. **Короткий** — 1 обобщённая цель на действие без учёта различий (без чар/прочности и т.п.).
2. **Расширенный** — больше вариативности (например разные зачарования), но не исчерпывающе.
3. **Сумашедший** — все возможные варианты **без учёта комбинаций** (предмет с 2 чарами засчитывается как 2 отдельных пункта прогресса, не как отдельная уникальная комбинация). Пространство большое, но конечное и вменяемое для датагена.
4. **«Я-КОНЧЕННЫЙ-СУКА-БЕГИТЕ-БЛЯТЬ»** — вообще все возможные предметы со всеми чарами **и их комбинациями**, со всеми стейтами (прочность у предметов, `BlockState` у блоков). Здесь пространство комбинаторно взрывается (например красящаяся кожаная броня — 16,777,216 значений RGB как параметр, а не как строка отдельных definitions).

**Критично**: для continuous/огромных дискретных пространств (цвет брони, паттерны баннеров, комбинации зачарований) — **не генерировать по JSON-файлу на каждое значение**. Вместо этого:
- Definition описывается как **предикат с параметром** («любое значение из диапазона», «N уникальных значений»), а не как перечисление всех значений.
- Прогресс по такой ачивке — не булев чек-лист «выполнено N из M заранее известных», а счётчик/сет уникальных увиденных значений, растущий по факту действий игрока (а не по размеру теоретического пространства).
- Компактное кодирование варианта — не сырой NBT/строка, а короткий value type (`VariantKey`, например упакованный `LongArray` для набора «id зачарования → уровень», или хэш для менее критичных случаев), с плотностью/точностью кодирования, зависящей от выбранного уровня density (1-2 — грубая агрегация, 3-4 — точная).
- Уровень 4 в части «все комбинации зачарований» ограничен уже самой игрой (несовместимые зачарования нельзя повесить вместе одновременно), так что «все комбинации» на практике имеет реальный, хоть и большой, потолок — не бесконечность.

Датаген должен поддерживать все 4 встроенных уровня плюс **полностью кастомный режим** — ручное задание цели (что за объект, какое действие, какое количество) и предиката через тот же JSON-формат, что и встроенные уровни, плюс опциональную награду (решает автор набора, не обязательна).

### Хранение прогресса игрока

`PlayerAchievementData` — на сервере, per-player. Реальный размер ограничен количеством **definitions** и **фактическими действиями конкретного игрока**, а не теоретическим размером комбинаторных пространств — не нужно опасаться «гигабайт» при разумном кодировании (см. `VariantKey` выше). Мод не рассчитан на масштаб публичного сервера с тысячами аккаунтов — это не повод для неряшливости, но не нужно оверинжинирить под нагрузку, которой не будет.

### Пакеты

- `S2C AchievementProgressUpdatePacket` — инкремент прогресса (батчить/троттлить при частых событиях).
- `S2C AchievementUnlockedPacket` — отдельно от update, для тоста/анимации на клиенте.
- `C2S RequestAchievementSyncPacket` / `S2C AchievementSyncPacket` — полный снапшот прогресса при входе в мир или по явному запросу.

## Клиентская часть (UI)

Экран прогресса (рабочее название `TabloScreen`) — НЕ дерево с рёбрами-зависимостями и **НЕ** свободный canvas с pan/zoom (эта идея была рассмотрена и сознательно отклонена — усложняла хит-тест и виртуализацию без реальной пользы). Финальная модель:

- Слева — сайдбар категорий (Blocks/Items/Entities). Активная категория должна быть визуально явно отличима от неактивных (не только тонкой акцентной полоской слева, одинаковой у всех пунктов, — нужен отдельный «selected»-стиль: фон/цвет текста).
- Справа — **вертикальный скролл**, без zoom и без drag-pan. Содержимое разбито на **группы по источнику предметов** (например `Minecraft`, `Create`, `IndustrialCraft2` — по мод-namespace), каждая группа со своим заголовком-разделителем. Заголовок группы стоит делать sticky (прилипает к верху видимой области, пока скроллится содержимое этой группы) — дёшево реализуется поверх той же арифметики, что и виртуализация.
- Внутри группы — сетка ячеек, которые **сами заполняют доступную ширину**: размер одной ячейки фиксирован (например 48×48, без масштабирования pixel-art иконок), а число столбцов в ряду пересчитывается из доступной ширины панели (`columnsCount = floor(availableWidth / cellSize)`), т.е. responsive по ширине окна, а не по высоте.
- Ячейки НЕ красные (это был только цвет плейсхолдера в мокапе) — нейтральный/серый слот, как ванильный инвентарный слот; акцентный цвет резервируется под рамки/выделение/hover, а не под сами слоты, иначе состояния теряются на одинаково «кричащем» фоне.
- Внутри ячейки рендерится **живое превью** объекта, а не статичная иконка:
  - для блока — вращающийся 3D-рендер блока (как в JEI/REI превью или recipe book), а не плоский 2D-спрайт;
  - для предмета — модель предмета в состоянии «валяется на земле» (как dropped item entity), с тем же покачиванием/вращением, что у него в мире;
  - для сущности — голова моба (или бюст), как обсуждалось для категорийной иконки — не отдельная 2D-иконка на первом этапе.
  - На первом проходе задачи №1 (см. `_tasks.md`) допустимо тестовое/заглушечное превью (даже просто силуэт/цвет), если полноценный live-рендер блока/итема/сущности внутри GUI-виджета требует отдельной проработки — но сама структура ячейки должна быть готова принять такой рендер без переделки.
- При наведении — тултип (имя, id, что уже сделано с объектом). При ЛКМ по ячейке — попап поверх экрана с расширенной информацией: требования ачивки, что выполнено/не выполнено (невыполненное помечается как «не изучено» / «больше N не изучено»). На первом проходе допустима тестовая/заглушечная информация в попапе — реальная интеграция с `PlayerAchievementData` идёт отдельным шагом.
- **Виртуализация**: рендерить и хит-тестить нужно только видимые ячейки. Так как контент теперь сгруппирован, сначала находится группа, на которую попадает текущий `scrollOffset` (по префиксным суммам высот групп: заголовок + `ceil(itemCount / columnsCount) * cellSize`), а уже внутри неё — диапазон видимых строк обычной арифметикой (`scrollOffset / cellSize`). Префиксные суммы высот пересчитываются только при смене ширины окна/фильтра/данных, не каждый кадр.
- Тултип и попап читают прогресс из уже засинхронизированного локального снапшота (вариант А — полный sync при входе), а не дёргают сервер на каждый ховер/клик. Для первого прохода, где реального прогресса ещё нет, — тестовые данные, но код должен читать их через тот же интерфейс/абстракцию, которым позже заменится реальный снапшот (не хардкодить тестовые данные внутрь виджета намертво).
- Известный баг, который уже был исправлен один раз: не полагаться на мутацию локальной переменной внутри замыкания hover-колбэка для смены цвета кнопки при наведении — состояние hover должно жить во внешнем поле (`hoveredRect`/id), проверяемом **до** отрисовки на каждом кадре, а не устанавливаемом постфактум чужим фреймом. Также маппы `clickEvents`/`hoverEvents` должны очищаться в начале каждого цикла рендера, а не расти бесконечно.

## Стиль кода и общие требования автора

- Верхнеуровнево: **без костылей**, чистая структура, предпочтение читаемости над компактностью.
- `sealed interface` вместо `enum class` там, где уместно моделировать варианты с данными.
- Godot-подобные нейминг и архитектурные паттерны (signals, node-tree-подобные структуры, `ready()`/`process()`-подобные жизненные циклы) — там, где это естественно ложится на клиент-часть/виджеты.
- Debugging эмпирический, не спекулятивный — при возникновении багов разбираться по фактическому поведению/логам, а не гадать.
- Изменения — точечные, по месту; не переписывать целые модули без необходимости.
- Verbose, читаемый код важнее лаконичности.
- Комментарии/сообщения в коммитах и обсуждении — автор общается на русском и английском; сам код (идентификаторы, комментарии в коде) — на английском, если не оговорено иное.

## Чего избегать

- Не изобретать свой DSL/язык предикатов с ручным парсером — используем JSON + рекурсивный codec.
- Не enumerate-ить комбинаторно-огромные пространства (цвета, паттерны, комбинации чар) как отдельные JSON-файлы в датагене.
- Не хранить клиентскую копию прогресса как источник истины — сервер всегда авторитетен.
- Не допускать конфликтов имён верхнеуровневых Gradle Kotlin DSL функций с методами `Task`/`Project` (см. историю с `property()`).
- Не тащить клиентские классы (рендер/GUI) в common/server-логику — сплит сорс-сетов существует именно для того, чтобы это было невозможно физически, а не по договорённости.
